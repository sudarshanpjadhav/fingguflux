# FingguFlux React Adapter: Technical Deep Dive

This report provides detailed answers to the architectural and operational questions regarding the @finggu/react adapter.

## 1. Mapping Injection Strategy

The `FingguProvider` supplies the `mapping.json` using **React Context**.

- **Mechanism**: The provider accepts a `mapping` prop and exposes it via `FingguContext`.
- **Injection**: Typically, the user performs a **Static Import** of the `mapping.json` generated by the compiler at the root of their application.
- **Runtime Fetch**: While static import is recommended for zero-latency, `FingguProvider` can also accept mapping data fetched at runtime (e.g., from a CDN) and update dynamically via state.
- **Hydration Safety**: Since the mapping is deterministic (based on stable hashes derived from class names), the class strings generated on the server (SSR) will exactly match those on the client, provided the same `mapping.json` is used. There is **zero risk** of hydration mismatch as long as the build artifacts are consistent.

## 2. Extreme Mode Safety (Deployment Sync)

If `mapping.json` changes between deployments, matching issues could occur IF the CSS bundle and JS bundle are out of sync.

- **Sync Strategy**: FingguFlux recommends serving both `index.css` and `mapping.json` as part of the same immutable build artifact (e.g., hashed filenames like `ff-build-v1.css`).
- **Version Mismatch**: If a client has an old JS bundle but a new CSS bundle, the mapping might point to non-existent classes.
- **Handling**:
  - **Graceful Fallback**: The `resolve` function returns the original `ff-*` name if no mapping is found, preventing completely empty class attributes.
  - **Pruning Check**: We recommend a CI/CD check to ensure the generated `mapping.json` is always bundled with the specific CSS it describes.

## 3. Prop → Class Resolution Flow

### Resolution Flow for `<Button variant="primary" size="lg" motion="fade" />`:

1.  **Input**: Props `{ variant: "primary", size: "lg", motion: "fade" }`.
2.  **Internal Map Lookup**: The component looks up the explicit strings in its internal maps:
    - `"primary"` → `ff-btn-primary`
    - `"lg"` → `ff-btn-lg`
    - `"fade"` → `ff-fade-in`
3.  **Composition**: `resolveAll(['ff-btn', 'ff-btn-primary', 'ff-btn-lg', 'ff-fade-in'])` is called.
4.  **Deduplication & Filtering**: `resolveAll` filters out falsy values.
5.  **Mode-Specific Mapping**:
    - **Dev Mode**: Returns `"ff-btn ff-btn-primary ff-btn-lg ff-fade-in"`.
    - **Extreme Mode**: Each class is looked up in `mapping.json`.
      - `ff-btn` → `ff-o4blxk`
      - `ff-btn-primary` → `ff-eb09xb`
      - ...
6.  **Output**: `"ff-o4blxk ff-eb09xb ..."`

## 4. Conditional Rendering & Tree-Shaking

The adapter is hardened against missing classes via **Explicit String Maps**.

```tsx
const VARIANTS = {
    primary: 'ff-btn-primary',
    secondary: 'ff-btn-secondary'
};
```

Even if the user writes `<Button variant={isPrimary ? "primary" : "secondary"} />`, the strings `'ff-btn-primary'` and `'ff-btn-secondary'` are present in the `Button` component source.
- **The Scanner** sees these full literals when scanning the library.
- **Tree-Shaking** works at the component level. If you don't import `Button`, its internal maps aren't loaded, and the scanner doesn't pick up its classes.

## 5. Dead Code Elimination (DCE)

If only `Button` is imported, the ESM build ensures that the code for `Tabs`, `Modal`, etc., is never included in the final JS bundle.

### Proof (Pseudo Build Analyzer Output)
```text
dist/main.js (Bundled)
├── @finggu/react/button.js (Included)
├── @finggu/react/provider.js (Included)
└── [TREESHAKEN] @finggu/react/tabs.js
└── [TREESHAKEN] @finggu/react/modal.js
```
Since the code is removed, the compiler scanner (which runs post-bundle or on source) will not find `ff-tabs` or `ff-modal` strings, and they will be pruned from the final CSS.

## 6. StrictMode Compatibility

Tested and compliant with React StrictMode.

- **No Double Event Bindings**: Interactive components (`Modal`, `Dropdown`) use `useEffect` with appropriate cleanup functions (`removeEventListener`).
- **No Side Effects on Mount**: State transitions (like body scroll locking in `Modal`) are triggered only by `isOpen` changes and correctly cleaned up.
- **No State Desync**: Uses controlled patterns for `Tabs` and `Modal`.

## 7. Server Components Safety (React 18+)

The adapter is **SSR Safe** and compatible with React 18+ streaming hydration.

- **Hooks**: All hooks are marked for Client use (`'use client'` directive is expected at the entry point or consumer level).
- **No useLayoutEffect**: Uses `useEffect` for all client-side side effects to avoid SSR warnings.
- **Static Logic**: The resolution logic itself is synchronous and pure, meaning it behaves identically during the initial server render and client hydration.

> [!IMPORTANT]
> To ensure 100% safety in Extreme mode, always verify that your `mapping.json` is generated for the exact set of components imported into your final bundle.
